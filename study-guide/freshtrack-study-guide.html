1The 30-second pitch

FreshTrack is a small web app that helps a household notice food before its label date passes. You add what you buy (name, quantity, fridge, freezer or cupboard, and the date on the label), and it shows the list with the soonest dates at the top.

I built it because I spent 19 years in food quality control, and I saw how much food is wasted simply because people forget what they have. My own household is the first user.

I use it to practise real DevOps end to end: tested code, a security-scanned container pipeline, and Kubernetes. Today the core runs on my local Kubernetes cluster. The morning reminder email, GitOps and the cloud trial are the next stages.

If you only remember one sentence

"It's a food expiry tracker for my household, and I use it to practise the full DevOps journey: from a Git commit, through a tested and scanned container pipeline, to Kubernetes."

The honest boundary (say this when asked "is it live?")

"It's not on the internet yet, on purpose. The grocery list is personal data, so before any public exposure it must sit behind HTTPS and a login prompt. The household trial on AWS is planned."

One rule worth quoting: FreshTrack organises reminders. It never says whether food is safe to eat. It also keeps "best before" (quality) separate from "expiration date" (a stricter date in Canada). That comes straight from your QC background, and interviewers like it.

2The big-picture diagram

This one diagram shows every part. Green boxes are built, the amber box is partly built, and dashed grey boxes are planned.

The restaurant version (memorise this)
  • web is the waiter. It takes your order and brings the plate, but never goes into the fridge.
  • api is the kitchen. It knows the rules and is the only one allowed into the fridge.
  • PostgreSQL is the walk-in fridge. Everything is stored there, even items that were used or thrown away (that is the trial record).
  • expiry-checker (planned) is the morning prep cook. Every morning it asks the kitchen "what needs using up?" and pins a note on the board (the email).
  • Kubernetes is the restaurant manager. It makes sure every station is staffed, and replaces a cook who collapses.
  • CI is the QC lab. No batch leaves the factory without passing inspection.
  • Docker Hub is the cold-storage warehouse where released batches wait for delivery.

Why only the api touches the database

If the web pages and the email checker each talked to the database, the rule "due within 3 days" would be written in two or three places, and one day they would disagree. With one kitchen, there is one set of rules. This is a written decision in docs/architecture.md (open decision 1, decided 9 Oct 2026).

3The journey of one request

Story A: "I add a carton of milk"

What is real today: steps from the api onwards run on Minikube, and I tested them with real groceries (milk and juice on 7 Nov). The web code exists and is tested on my laptop. The web Pod and the Ingress with HTTPS + basic auth are Planned.

  1. The form. You fill in five fields. The page includes a hidden CSRF token, a signed ticket that only FreshTrack's own pages can produce. A fake form on another website would not have it.
  2. web forwards it. web turns the form into JSON and sends it to http://api/items. api is a Kubernetes Service name, a stable internal phone number.
  3. api checks it. validation.py checks the name (1–100 characters), the quantity, the location (only fridge, freezer or cupboard), a real date, and the date type. It returns all problems at once, not one at a time.
  4. The database checks it again. schema.sql has CHECK rules. Even if someone skipped the api, the fridge would refuse a "garage" location.
  5. The answer goes back as 201 Created. web shows the list, split into "past date", "soon" and "later".

Story B: "7 a.m., the morning email goes out" Planned / not yet built

Nothing in this story exists in code yet. The expiry-checker, Mailpit and the "due items" api endpoint are milestone 5. 07:00 is a proposal (open decision 4), and "no email when nothing is due" is also a proposal (open decision 5). Describe it as "how it will work".

Analogy

The CronJob is the alarm clock on the prep cook's phone. At 7 a.m. Toronto time it wakes up a temporary cook (a Pod), who asks the kitchen for the "use soon" list, writes one note, posts it, and goes home. If the cook doesn't finish, the manager records it as Failed. Later, an alert will ring.

4Unit by unit

Each card covers the same six things: what it is, why you chose it, the key file, how it connects, what could break, and the official docs. Built parts come first, then planned ones.

A. Source control and the delivery pipeline

Git + GitHub, with a protected main branch Built

What it is
Git records every change to the code, and GitHub stores that history online. A ruleset called protect-main says nobody, not even the owner, can push straight to main. Every change goes through a pull request (PR), the CI job checks must pass, SonarCloud must pass, and only squash merges are allowed.
Analogy
Git is the batch record book: every change has a date, an author and a reason. The ruleset is the rule that no batch leaves the plant without QC release, with no back door, even for the plant manager.
Why I chose it
GitHub is the most common place recruiters look. Alternative: GitLab. I added the ruleset before the SHIP stage, because once every push to main publishes an image, a direct push would publish unchecked code.
Key evidence
No file: it's a GitHub setting. Proof from the Entry 6 drill: git push origin main was refused with GH013: Repository rule violations found. You proved the lock works by trying to break it.
How it connects
Every push starts GitHub Actions CI. Merges to main start the SHIP job.
What could break, and how I'd notice
If someone added themselves to the bypass list, unchecked code could ship. I would notice in the ruleset settings and in the GitHub API, which is the source of truth (a screenshot once hid part of the list).
Docs
GitHub: About rulesets

GitHub Actions CI Built (for the api)

What it is
A robot that runs on GitHub's computers every time you push. It follows the recipe in .github/workflows/ci.yml: check the code, test it, scan it, build the image, prove it starts, scan the image, and (only on main) ship it. The full picture is in section 6.
Analogy
The production line with QC checkpoints: raw-material inspection, cooking, taste test, lab release, dispatch. If any checkpoint fails, the line stops.
Why I chose it
It is built into GitHub, so there is no server to run. Alternatives: GitLab CI and Jenkins. (You deliberately did not use Jenkins here.)
Key file
.github/workflows/ci.yml. Two jobs: checks (every branch and PR) and ship (push to main only).
What could break
An invalid YAML file. This really happened (Entry 3): the workflow showed no jobs at all, only a failed run named after the file path. Lesson: "no red is not the same as green". Check that the jobs actually ran.
Docs
GitHub Actions documentation

Code checks: Ruff, pytest, Bandit, SonarCloud Built (api only in CI)

What they are
Ruff checks style and common mistakes (a linter and formatter). pytest runs the tests: 61 api tests in CI, including 11 against a real PostgreSQL. Bandit looks for risky Python patterns. SonarCloud reviews code quality and security "hotspots" through its own GitHub app (Automatic Analysis), not as a step in ci.yml.
Analogy
Ruff is the label and spelling check on packaging. pytest is the taste and weight test: does each product do what the spec says? Bandit and SonarCloud are the food-safety auditor walking the line looking for hazards.
Why
Ruff is very fast and replaces several older tools. SonarCloud is free for public repos. Alternatives: SonarQube Community (self-hosted) and Semgrep (instead of Bandit).
Real catches
Ruff found 3 problems the author missed (Entry 3). SonarCloud flagged pip install without --only-binary (a source package can run code during install), installing without hash locks, missing ephemeral-storage limits, and a path-traversal risk in the web client.
Two kinds of test
Unit tests replace the database with a fake, so they are fast and prove the Python logic. Integration tests use a throwaway PostgreSQL (a CI "service container") and prove the SQL, sorting and CHECK rules.
What could break
Gap CI does not test web/ yet. The web code was merged after local tests only. Adding it to CI is the very next task.
Docs
Ruff · pytest · Bandit · SonarQube Cloud (SonarCloud) · Service containers

Container image (Dockerfile) Built (api)

What it is
An image is a sealed package with the app, Python and every library it needs, so it runs the same on my laptop, in CI and in Kubernetes. A running copy of an image is a container.
Analogy
A vacuum-sealed meal kit: the recipe and every ingredient in one box, so any kitchen can cook the same dish. The digest (sha256:…) is the lot number: it identifies one exact batch, and it can't be relabelled.
Why I chose this design
A hardened image: base image pinned by digest, hash-locked dependencies, non-root user, small size. Single-stage, because every package installs as a ready-made wheel, so there are no build tools to leave behind. Alternative registries and builders exist (Podman, Buildah), but Docker is the standard.
Key file: api/Dockerfile
# Exact base image, pinned by digest (the lot number)
FROM python:3.12.15-slim-trixie@sha256:a6e34c59...11b1

# Temporary security patches until the base image includes them
RUN apt-get update \
 && apt-get install -y --no-install-recommends --only-upgrade \
      apt=3.0.4 libapt-pkg7.0=3.0.4 \
      zlib1g=1:1.3.dfsg+really1.3.1-1+deb13u1 ...

# Only ready-made wheels, each checked against its hash
RUN pip install --no-cache-dir --only-binary :all: --require-hashes -r requirements.txt

# Run as a numbered, non-root user with no home and no login
RUN useradd --uid 10001 --no-create-home --shell /usr/sbin/nologin freshtrack
USER 10001

CMD ["gunicorn", "--bind", "0.0.0.0:8000", "--no-control-socket", "app:create_app()"]
Read it like this: a fixed base → patch two known holes → install exactly the locked libraries → become a non-root user → start the production web server, gunicorn.
Numbers you can quote
216 MB locally, 52.5 MB compressed on Docker Hub (Entries 5–6).
What could break
gunicorn tried to create a control socket in a home folder the user doesn't have, which gave "Permission denied" (Entry 5). Fixed with --no-control-socket.
Docs
Dockerfile reference · gunicorn

Trivy (vulnerability and secret scanner) Built

What it is
A scanner that compares every package in your code and image with public lists of known security holes (CVEs). It also looks for passwords left in files. It runs twice: once on the source files (fs), and once on the finished image.
Analogy
The lab test for contaminants. The full report lists everything found. The gate holds the batch only for HIGH or CRITICAL problems that have a fix available. Problems with no fix are recorded and watched, because there is no corrective action yet.
Why I chose it
One tool for packages, images and secrets. Alternative: Grype, or pip-audit plus gitleaks. I run Trivy from its official image pinned by digest, not through trivy-action, because that action's tags were hijacked in March 2026. A digest can't be swapped.
Key snippet (the gate)
image --scanners vuln,secret
  --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1
  --input /image.tar   # read-only file, no Docker socket
Real catches
A drill with an old 2024 base image gave 557 Debian findings, and the gate failed while everything else stayed green. A real failure on 10 Nov: two fixable HIGH zlib CVEs appeared with no code change, because the vulnerability list had grown.
What could break
Image scans only run when I push, so a new CVE could sit unnoticed for weeks. A weekly scheduled re-scan is Planned.
Docs
Trivy documentation

Docker Hub (image registry) Built

What it is
An online store for images. CI pushes samayohub/freshtrack-api:<git commit SHA>. The repository is public, so interviewers can pull it.
Analogy
The cold-storage warehouse. Only QC-released batches go in, each labelled with its batch number (the commit SHA), never "latest".
Why
It is free and well known. Alternative: Harbor (self-hosted, with built-in scanning). For AWS, also pushing to ECR is a recorded option.

B. The application

api (Flask) Built

What it is
A small Python program that answers web requests with JSON. It holds all the rules and is the only part that talks to the database. Flask is a light Python web framework.
Analogy
The kitchen. Orders come in through a hatch (HTTP), the kitchen checks them against the recipe book, and only the kitchen opens the fridge.
Endpoints
RequestWhat it does
GET /health"I'm alive." Never checks the database.
GET /ready"I can serve." Runs SELECT 1 on the database with a 2-second timeout.
GET /itemsActive items, soonest date first. ?status=closed lists used and discarded items.
POST /itemsAdd an item. 201 if saved, 400 with every error.
GET /items/<id>One item, or 404.
PUT /items/<id>Fix the details of an active item. 409 if it is already closed.
PATCH /items/<id>Mark it used or discarded. The row is kept, never deleted.
Key file: api/app.py
@app.get("/health")
def health():
    # Liveness: no database check here, otherwise a database outage
    # would make Kubernetes restart healthy api Pods.
    return jsonify(status="ok"), 200

@app.get("/ready")
def ready():
    # Readiness: only accept traffic when the database is reachable.
    if database_is_reachable(app.config["DATABASE_URL"]):
        return jsonify(status="ready"), 200
    return jsonify(status="not ready"), 503
This split is one of the most common interview topics. If the database goes down, restarting the api would not fix it, so /health stays green and only /ready goes red.
Why Flask
It is small and easy to read for someone new. Alternatives: FastAPI and Django. gunicorn runs it in production; Flask's own server is only for development.
Error handling
Any database error returns 503 "Database unavailable.". Only the error type is logged, never connection details that could include the password.
What could break
The table is missing: /ready is still 200 (it only checks the connection), but /items returns 503, and the log says UndefinedTable. This happened in Entry 10, and it is why the init-db Job exists.
Docs
Flask · psycopg 3 (PostgreSQL driver)

Data rules: schema.sql, validation.py, db.py Built

What it is
One table, items, with rules enforced by the database itself. Python checks the input first, and all SQL lives in one file.
Analogy
Goods-in inspection happens twice: at the loading dock (validation.py) and at the shelf (database CHECK rules). Even a delivery that sneaks past the dock is refused at the shelf.
Key file: api/schema.sql
CREATE TABLE IF NOT EXISTS items (
    id         integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    location   text NOT NULL CHECK (location IN ('fridge', 'freezer', 'cupboard')),
    label_date date NOT NULL,
    date_type  text NOT NULL CHECK (date_type IN ('best_before', 'expiration')),
    status     text NOT NULL DEFAULT 'active'
                    CHECK (status IN ('active', 'used', 'discarded')),
    closed_at  timestamptz,
    -- active has no closed time; used/discarded always has one
    CHECK ((status = 'active') = (closed_at IS NULL))
    ...
);
IF NOT EXISTS makes it safe to run twice (idempotent). An index matches the "active, soonest first" list exactly.
No SQL injection (db.py)
conn.execute("SELECT ... FROM items WHERE id = %s", (item_id,))
Values travel separately from the SQL text. A food name like '); DROP TABLE items;-- is just a strange name, never a command.
What could break
A wrong sort order, or a CHECK rule removed by mistake. Integration tests against a real PostgreSQL in CI would catch it.
Docs
PostgreSQL: constraints · psycopg: passing parameters

web (Flask + HTML templates) Partly built

What it is
The pages people see: home (what's at home, grouped "past / soon / later", with a location filter), add food, edit, and history (used vs discarded in the last 7 days). Plain HTML and CSS, with no JavaScript at all.
Honest status
The code is merged (PR #23) with about 60 tests that pass on my laptop. It is not yet in CI, there is no Dockerfile, and it is not deployed to Minikube.
Analogy
The waiter and the menu. It speaks plain language to the customer, then passes the order to the kitchen.
Security features
  • CSRF protection (Flask-WTF): every form carries a signed token, so another website cannot submit forms on your behalf.
  • Content-Security-Policy header: only our own styles, no scripts, and no showing our pages inside another site.
  • Cookies are HttpOnly (scripts can't read them) and Secure (HTTPS only).
  • item_path() only accepts a positive whole number as an id, so nobody can steer a request to another api address (path traversal, found by SonarCloud).
  • It uses the household's time zone (America/Toronto), not the server's, to decide what "today" is.
Key file: web/api_client.py
def item_path(item_id):
    number = int(item_id)          # "../ready" is refused here
    if number < 1:
        raise ValueError("item_id must be a positive whole number")
    return f"/items/{number}"
What could break
The api is down: web shows a friendly error page with status 503, and its own /ready fails, so Kubernetes would stop sending it traffic.
Docs
Flask templates · Flask-WTF CSRF · MDN: Content Security Policy

C. Kubernetes on Minikube

Kubernetes in one paragraph

Kubernetes is software that runs containers for you and keeps them running. You write down what you want in YAML files ("one api cook on duty, using this exact meal kit"), and Kubernetes works constantly to make reality match. If a cook collapses, it hires a new one. This is called desired state, and it is like a par level on a stock sheet: when the shelf drops below par, it gets restocked automatically.

Minikube cluster with Calico Built

What it is
A full Kubernetes cluster running on my laptop (WSL Ubuntu with Docker Desktop). Profile freshtrack: Kubernetes v1.36.4, the containerd runtime, and Calico for networking, which can enforce NetworkPolicies.
Analogy
A test kitchen built to the same layout as the real restaurant, so the opening night (the AWS trial) has no surprises.
Why
It is free, and it is my main lab. I matched it to the planned k3s cluster on AWS: same Kubernetes minor version (1.36), same runtime, and network policies that are really enforced. Alternative: kind.
What could break
It happens often: Docker Desktop is off, so the cluster is down. kubectl then says connection refused to 127.0.0.1:8080. Check minikube profile list and start it again. The data survived every restart.

api Deployment (with its ReplicaSets, Pods and probes) Built

What it is
A Pod is one running copy of the app (one or more containers). A ReplicaSet keeps the right number of identical Pods for one version. A Deployment manages ReplicaSets, so it can roll out a new version gradually and roll back.
Analogy
A Pod is one cook at the api station. The ReplicaSet is this week's roster for one recipe version. The Deployment is the head chef's staffing plan: "always 1 cook on api; when the recipe changes, bring in the new cook first, and send the old one home only when the new one is ready."
Key file: deploy/k8s/api-deployment.yaml
image: samayohub/freshtrack-api:bc2b049...@sha256:c29f61b5...  # tag + digest
automountServiceAccountToken: false     # api never talks to Kubernetes
securityContext: { runAsNonRoot: true, runAsUser: 10001 }
  ... allowPrivilegeEscalation: false, capabilities: drop ["ALL"]
resources:
  requests: { cpu: 50m,  memory: 96Mi,  ephemeral-storage: 64Mi }
  limits:   { cpu: 250m, memory: 192Mi, ephemeral-storage: 256Mi }
startupProbe:   /health  every 2s, up to 15 failures  # has it booted?
readinessProbe: /ready   every 5s, timeout 3s         # can it take orders?
livenessProbe:  /health  every 10s                    # is it still alive?
The three probes, kitchen version
  • Startup probe: "Is the oven warmed up yet?" The other probes wait until this passes.
  • Readiness probe: "Is the station ready to take orders?" If it says no, the waiter stops sending orders to it, but nobody fires the cook.
  • Liveness probe: "Is the cook still conscious?" If it says no 3 times, Kubernetes restarts the container.
Requests and limits
The request is the reserved seat (50 milli-CPU means 5% of one CPU). The limit is the ceiling. Going over the memory limit gets the container killed (OOMKilled). Ephemeral storage is the container's scratch disk; SonarCloud asked for limits there too.
Why tag and digest
The tag tells a human which commit it is. The digest guarantees the cluster runs the exact bytes CI scanned.
What could break, and what I saw
  • No database: the Pod shows Running but READY is 0/1. "Running is not Ready." (Entry 7)
  • A rollout looked stuck with 2 Pods: that was a safety feature. With 1 replica the new Pod must be Ready before the old one leaves.
  • A kubectl rollout undo made the cluster drift from Git (an old image came back and /items returned 404). Fixed by re-applying the file (Entry 10). Argo CD will catch this automatically later.
Docs
Deployments · Probes · Requests and limits · Pod security standards

Service api (ClusterIP) Built

What it is
A stable internal address and name (api, port 80) that forwards to whichever api Pods are Ready. Pod IPs change every time a Pod is replaced; the Service name never does. ClusterIP means it can only be reached from inside the cluster.
Analogy
The internal phone extension "kitchen". You don't need to know which cook is on shift. The call rings whoever is on duty and ready.
Key file
deploy/k8s/api-service.yaml: port: 80 → targetPort: http (the named container port 8000). It selects Pods by label.
Why ClusterIP
The api has no login, so it must not be reachable from outside. Only the web Pod (and the planned checker) will call it.
What could break
A wrong selector label leaves the Service with no endpoints, and callers get "connection refused" in milliseconds. This drill is saved for game day.

PostgreSQL: StatefulSet + headless Service + PVC Built

What it is
PostgreSQL 18.6 is the database. A StatefulSet runs it with a stable name (postgres-0) and its own disk. A PersistentVolumeClaim (PVC) is the request for that disk (1Gi). A PersistentVolume (PV) is the actual disk. A StorageClass is the type of disk (standard on Minikube, local-path on k3s). A headless Service (clusterIP: None) gives the Pod a stable DNS name without a load-balancer in between.
Analogy
The walk-in fridge with a name plate. If the fridge door (the Pod) breaks and is replaced, the new door is fitted to the same fridge, with all the food still inside. The PVC is the reserved shelf space on the order slip, the PV is the shelf itself, and the StorageClass is the shelving supplier.
Key file: deploy/k8s/postgres-statefulset.yaml
image: postgres:18.6-trixie@sha256:3a426452...   # official, pinned
persistentVolumeClaimRetentionPolicy: { whenDeleted: Retain, whenScaled: Retain }
terminationGracePeriodSeconds: 60                # time to shut down cleanly
volumeMounts:
  - name: data
    mountPath: /var/lib/postgresql   # PostgreSQL 18 changed this path!
volumeClaimTemplates:
  - metadata: { name: data }
    spec: { accessModes: ["ReadWriteOnce"], resources: { requests: { storage: 1Gi } } }
Why not a Deployment
Deployment Pods are interchangeable and get random names. A database needs a stable identity and its own disk that follows it. Alternative: a managed database such as Amazon RDS, which is a good answer for a real business.
Proof (Entry 9)
I wrote a test row, deleted postgres-0, and a new postgres-0 was back in about 5 seconds with a new IP, the same disk and the same row. The log said "database directory appears to contain a database; skipping initialization". The api stayed Ready.
What could break
Mounting the old path /var/lib/postgresql/data would have left the data off the persistent disk. It would work until the first restart, and then everything would be gone. I found this by reading the official image docs.
Docs
StatefulSets · Persistent Volumes · Headless Services · Official postgres image · PostgreSQL versioning policy

Job init-db Built

What it is
A Job runs a Pod until a task finishes successfully once, then stops. This one runs python init_db.py using the same api image and Secret, to create the items table.
Analogy
A one-off deep-clean task on the rota: do it, tick it off, go home. A Deployment would keep "re-hiring" a cook who has finished on purpose.
Key file: deploy/k8s/init-db-job.yaml
backoffLimit: 3               # retry up to 3 times
activeDeadlineSeconds: 120    # give up after 2 minutes
ttlSecondsAfterFinished: 3600 # tidy up after 1 hour
restartPolicy: Never          # each retry is a new Pod; failed Pods keep their logs
command: ["python", "init_db.py"]
The contract
The exit code: 0 means done and the Job is Complete; anything else means retry. Completed 0/1 is success, not a broken Pod.
What could break
You can't apply a changed Job over an old one (the Pod template is immutable), which is why the TTL is there. A volume does not protect against a bad command, so the SQL never uses DROP.
Docs
Kubernetes: Jobs

6The CI/CD pipeline

CI (Continuous Integration) checks and packages every change. CD (Continuous Delivery or Deployment) gets the package running. In FreshTrack, CI is fully built for the api. CD is still manual: I update the image line in Git and run kubectl apply.

The food-factory version
StageFactoryWhat it catches
CHECKIncoming raw-material inspectionMessy or broken code
TESTRecipe trial against the specWrong logic, wrong SQL, wrong sorting
SCAN CODESupplier certificate checkRisky code, vulnerable libraries, passwords in files
BUILDProductionA recipe that can't be cooked (Dockerfile errors)
PROVETaste test on the lineAn image that builds but won't start
SCAN IMAGEQC lab releaseHoles brought in by the base image you didn't write
SHIPDispatch to the warehouseNothing new: it only releases what passed every gate

Five security choices in the pipeline worth knowing

  1. Every action pinned to a full commit SHA (for example actions/checkout@3d3c42e5…), each checked against its real release tag. Tags can be moved by an attacker; a SHA can't.
  2. Read-only token (permissions: contents: read), and checkout keeps no Git credentials on the runner.
  3. The Docker Hub token is locked to main through a GitHub environment. Branches and PRs never see it.
  4. Ship the exact scanned file. The image travels as an artifact from checks to ship. Rebuilding would create a new, unscanned image under the same name.
  5. Trivy reads a tar file, never the Docker socket, which would mean root-level control of the runner.
Honest limits of today's pipeline
  • web/ is not linted, tested or built in CI yet.
  • No scheduled weekly re-scan yet.
  • No Git-history secret scan (gitleaks), and no misconfiguration scan of the Dockerfile and YAML.
  • Unfixed HIGH vulnerabilities pass the gate on purpose. They stay visible in the full report.
  • Deployment is manual. Argo CD is planned.

7Secrets and security

The analogy: the restaurant's key box

The fridge key (the database password) is never written in the recipe book (Git), and never sealed inside the meal kit (the image). Today the manager (me) puts the key in a locked box in the office (a Kubernetes Secret) by hand. The recipe book only says "the key is in box postgres-credentials, slot DATABASE_URL".

In the planned setup, a bank vault (OpenBao) holds the master copy. A courier (External Secrets Operator) checks the vault regularly and refills the office box. When the key changes, a shift supervisor (Reloader) tells the cooks to come back in, so they pick up the new key.

Today Built

# In the Deployment: a pointer to the Secret, never the value
env:
  - name: DATABASE_URL
    valueFrom:
      secretKeyRef:
        name: postgres-credentials
        key: DATABASE_URL
  • The password came from openssl rand -hex 24. It uses hex characters only, because @ / : would break the database URL.
  • Least privilege: each Pod gets only the keys it needs. The database never sees DATABASE_URL; the api never sees the separate password key.
  • Verified without exposing it: kubectl describe secret shows only key names and byte sizes, and I compared the sizes with the expected lengths.
  • Important fact: Kubernetes Secrets are only base64-encoded (a sealed envelope, not a safe). Protection comes from access control (RBAC) and encryption of the cluster's database, and from never putting the values in Git.

Planned Planned / not yet built

Why Reloader? A Secret is read as an environment variable only when the container starts. If the password changes, running Pods keep the old one until they restart. Reloader triggers that restart automatically.

Other security layers (a quick list for interviews)

Built
  • Non-root containers (api UID 10001, postgres 999), all Linux capabilities dropped, no privilege escalation, seccomp RuntimeDefault
  • No Kubernetes API token mounted in any Pod

  • Base images and actions pinned by digest or SHA; hash-locked Python packages

For technical interviewers

Technical7. Walk me through the architecture.

"Four parts. A web front end and an api, both Flask; PostgreSQL; and a planned expiry-checker CronJob for the morning email. Only the api touches the database, so the business rules live in one place. On Minikube I have a namespace with the api Deployment behind a ClusterIP Service, PostgreSQL as a StatefulSet with a persistent volume behind a headless Service, the credentials in a Secret, and a Job that creates the table. Code goes through GitHub Actions to Docker Hub, and today I deploy with kubectl apply. Argo CD is planned."

Technical8. Why a StatefulSet for PostgreSQL instead of a Deployment?

"A database needs a stable identity and its own disk. A StatefulSet gives the Pod a fixed name, postgres-0, and creates a PersistentVolumeClaim for it from a template. If the Pod is deleted, the new postgres-0 reattaches the same volume. I tested that: I wrote a row, deleted the Pod, and it came back in about five seconds with a new IP but the same data. A Deployment's Pods are interchangeable with random names, which is right for the stateless api, not for a database. For a real business I'd probably use a managed database like RDS."

Technical9. Explain liveness, readiness and startup probes. Why doesn't /health check the database?

"Startup asks 'has it finished booting?' and holds off the others. Readiness asks 'can it take traffic?'; if it fails, the Service stops sending requests, but nothing restarts. Liveness asks 'is the process stuck?'; if it fails, Kubernetes restarts the container. My /ready checks the database, and /health doesn't. If the database goes down, restarting the api can't fix it. It would only cause a restart loop. I proved that in my first drill."

Technical10. What happens if a Pod dies?

"For the api, the ReplicaSet sees it has zero of one Pods and creates a new one. The Service only routes to Ready Pods, so traffic resumes once the new one passes readiness. Honestly, with one replica there is a short gap. That's why the game-day stage scales the api to three replicas with a PodDisruptionBudget. For the database, the StatefulSet recreates postgres-0 with the same volume, so no data is lost."

Technical11. How do you handle secrets?

"Never in Git or in an image. Today the database credentials are a Kubernetes Secret I create by hand from a file outside the repo, and Pods reference it with secretKeyRef, so Git only holds the name. Each Pod gets only the keys it needs. I know Secrets are only base64-encoded, so access control matters. The plan is OpenBao as the vault, External Secrets Operator to sync it, and Reloader to restart Pods when it changes. In CI, the Docker Hub token sits in a GitHub environment that only the main branch can use."

Technical12. Walk me through your CI pipeline.

"Every push runs one job: Ruff lint and format, pytest with unit tests plus integration tests against a throwaway PostgreSQL service container, Bandit, and a Trivy scan of the source. Then it builds the image tagged with the commit SHA, starts it and curls /health, saves it as a tar and runs a Trivy image scan: a full report, plus a gate that fails on fixable HIGH or CRITICAL. On main only, a second job loads that exact tar and pushes it to Docker Hub. SonarCloud must also pass, and main is protected by a ruleset."

Technical13. Why pin actions to SHAs and images to digests?

"Tags can move. Someone with access can point v1 at different code. In March 2026, trivy-action's tags were hijacked to deliver malicious code. A commit SHA or an image digest is a fingerprint of the exact content, so it can't be swapped. I verify each SHA against the real release tag, because AI tools have suggested invented SHAs before."

Technical14. How do you handle vulnerabilities? Give an example.

"The gate blocks only what I can act on: HIGH or CRITICAL with a fix available. Everything else stays visible in the full report. One day a PR with no image change failed the gate: two new HIGH CVEs in zlib had been published. I checked the Debian security tracker, because the scanner's title was mislabelled, then upgraded just that package to the fixed version, pinned, with a comment to remove the patch when the base image catches up. I didn't add an ignore rule."

Technical15. Why not tag images as latest?

"latest tells you nothing and changes under you. Every image I push is tagged with the git commit SHA, so I always know exactly which code runs, and a rollback means choosing an older SHA. In Kubernetes I also add the digest, so the cluster runs the exact bytes CI scanned."

Technical16. Why Argo CD? How does code get to the cluster today?

"Today it's manual: I update the image tag and digest in the Deployment file through a PR, then run a server-side dry run and kubectl apply. I hit the downside: after a rollout undo, the cluster ran an old image that no longer matched Git, and I only found it when an endpoint returned 404. Argo CD is planned to fix that. It continuously compares the cluster with Git and corrects drift. CI pushes, GitOps pulls, and the cluster needs no credentials from CI. The alternative is Flux."

Technical17. Why Minikube first, and why k3s rather than EKS?

"Minikube is free, so it's my main lab. I made it match the planned k3s cluster: Kubernetes 1.36, containerd, and Calico so network policies are actually enforced. Problems show up at home, not on a paid cloud server. For a one-week household trial, k3s on one EC2 instance is far cheaper than EKS, which charges for its control plane. For a real company with a team, EKS or another managed service would make sense."

Technical18. How do you protect the data from bad input or SQL injection?

"Two layers. The api validates every field and returns all errors at once. The database has CHECK constraints for the same rules, so even a bug in Python can't store a bad location or status. All SQL lives in one file and passes values as parameters, never pasted into the query text, so input can't become a command. Used and discarded items are never deleted; they keep a closed time, because that's the trial data."

Technical19. How would you troubleshoot a Pod that isn't Ready?

"kubectl get pods to see READY versus STATUS. Running but 0/1 means readiness is failing. Then kubectl describe pod for the probe events and status codes, kubectl logs for the reason, and kubectl get endpointslices to see whether the Service has ready endpoints. In my case the readiness probe returned 503 because there was no database yet, so the Service had endpoints listed but none ready, and even /health was refused through the Service."

Technical20. How do you test?

"Unit tests replace the database with fakes, which is fast and proves the Python logic. Integration tests run against a real PostgreSQL, the same pinned image as the cluster, started as a service container in CI, which proves the SQL, constraints and sorting. That moved us from 50 passed and 11 skipped to 61 passed and 0 skipped. Then there's a smoke test that starts the real image and calls /health. One honest gap: the web tests run on my laptop but aren't in CI yet. That's my next task."

Technical21. What would you change if this had 10,000 users?

"None of this is built, but the main changes would be:

  • real user accounts through an identity provider, and a household ID on every row;
  • a managed PostgreSQL with backups, point-in-time recovery and a replica, plus connection pooling;
  • several api and web replicas across nodes and zones, with an HPA, PodDisruptionBudgets and a managed cluster like EKS;
  • email through a production email service with a queue and retries, not one CronJob looping over everyone;
  • proper observability with SLOs and alerts;
  • separate staging and production environments promoted through GitOps.

For one household, all of that would be over-engineering."

Technical22. How is the app secured inside Kubernetes?

"Containers run as non-root with all Linux capabilities dropped, no privilege escalation, and the default seccomp profile. No Pod gets a Kubernetes API token, because none needs one. The api and database are only reachable inside the cluster. Every container has CPU, memory and ephemeral-storage requests and limits, so one can't starve the node. NetworkPolicies and TLS with basic auth at the edge are the next security stage."

11Self-check quiz

Answer out loud or on paper, then open the card. Aim for 8 out of 10, and re-read section 4 for any miss.

1. Which FreshTrack component is the only one allowed to talk to the database, and why?

The api. The rules (validation, "due within 3 days") live in one place, so web and the checker can never disagree.

2. Your api Pod shows STATUS Running but READY 0/1. What does that mean, and what's the first likely cause?

The process is alive but the readiness probe fails, so the Service sends it no traffic. In FreshTrack, /ready fails when the database can't be reached. Check kubectl describe pod and kubectl logs.

3. Why does /health not check the database?

It is the liveness probe. If it checked the database, a database outage would make Kubernetes restart healthy api Pods in a loop, and restarts can't fix the database.

4. You delete postgres-0. What stays the same and what changes?

Same: the Pod name, the DNS name, the PVC/disk and the data. Changes: the Pod IP. In the drill it was back in about 5 seconds.

5. What does the Trivy gate fail on, and what happens to everything else?

HIGH or CRITICAL vulnerabilities that have a fix (--severity HIGH,CRITICAL --ignore-unfixed). Everything else still appears in the full report step, which never fails.

6. Name the two locks that stop a feature branch from shipping an image to Docker Hub.

(1) The ship job runs only on a push to main (its if: condition). (2) The Docker Hub token lives in the dockerhub environment, which only main may use. The protect-main ruleset also means main only changes through a checked PR.

7. Why does the ship job load an artifact instead of rebuilding the image?

To push the exact bytes that were scanned. A rebuild could pull newer packages and produce a new, unscanned image with the same name.

8. How does the database password reach the api without being in Git? What is planned to improve it?

A Secret is created by hand from a file outside the repo, and the Deployment uses secretKeyRef (only the name is in Git), so the value becomes an environment variable at start. Planned: OpenBao → External Secrets Operator → Secret, with Reloader restarting Pods when it changes.

9. Why is the table created by a Job and not a Deployment? What makes it safe to run twice?

A Job runs until the task succeeds once and then stops; a Deployment would keep restarting a finished script. It's safe because schema.sql uses CREATE TABLE/INDEX IF NOT EXISTS and never DROP (idempotent).

10. Which of these are built today: web on Minikube, the morning email, Argo CD, Helm, the api on Minikube, Trivy in CI?

Built: the api on Minikube and Trivy in CI. Not built: web on Minikube (the code is merged but not deployed or in CI), the morning email, Argo CD and Helm, which are all planned.
