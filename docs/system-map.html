FreshTrack

A household food expiry tracker. You record what goes into the fridge, freezer or cupboard, the app lists what is closest to its label date, and a morning email names what to use up next.

Why it exists

Food gets thrown away because people forget it

Out of sightYogurt at the back of the fridge is found two days after its date.
Bought twiceNobody remembers there is already an open jar in the cupboard.
Two kinds of date"Best before" is about quality. "Expiration date" is a hard limit. Reminders word them differently.
No safety adviceFreshTrack organises reminders. It never says whether food is safe to eat.

How a household uses it

Everything inside the shaded box runs in one Kubernetes namespace, freshtrack.

Flow A · Adding an item

  1. Someone fills in the form on the web page: name, quantity, fridge / freezer / cupboard, label date, and best before or expiration date.
  2. web sends it to the api as JSON (POST /items).
  3. The api checks every field, then saves it. The table repeats the same rules, so bad data cannot get in another way.
  4. The list comes back with the soonest date at the top (GET /items).
  5. Marking an item used or discarded (PATCH /items/<id>) removes it from the list but keeps the row for the trial data.

In progress These three api routes are written and tested, waiting for review. The web pages come next.

Flow B · The morning reminder

  1. A Kubernetes CronJob starts the expiry-checker each morning, Toronto time.
  2. It asks the api for active items within 3 days of their date, or already past it.
  3. It builds one email, with "Best before" and "Expiration date" items worded differently.
  4. It sends the email to the one household address, which is kept in a Secret, not in the database.
  5. It exits. Success or failure shows in the Job status and logs, which is where an alert will look.

Planned Milestone 5. Mailpit catches every email in testing, so no real email is sent by accident.

Secrets, monitoring and networking

Each shaded box is its own namespace, like separate rooms in one building. The app stays in freshtrack; the tools that look after it live next door.

Secrets flow

  1. The database password is stored once, in OpenBao.
  2. External Secrets Operator reads it with its own narrow permission.
  3. It creates the Kubernetes Secret postgres-credentials, replacing today's manual step.
  4. When the password changes, Reloader restarts the api and database Pods so they read the new value.

Planned Milestone 4, after Helm. OpenBao gets a small PVC so its data survives restarts.

Observability flow

  1. Prometheus scrapes numbers from the api and the cluster every few seconds.
  2. Grafana Alloy runs one Pod on every node (a DaemonSet) and ships container logs to Loki.
  3. Grafana shows metrics and logs side by side on one dashboard.
  4. Alertmanager sends an alert when a rule fires, for example "the morning reminder did not run".

Planned Milestone 6. This is what lets game days start from an alert instead of a guess.

Evidence

Things that actually happened

Each one is recorded in the engineering journal with the commands and output.

Vulnerable image blocked

An old base image built and passed its health check, but failed the Trivy image gate, so it never reached Docker Hub.

Branch protection tested

A direct push to main was rejected (GH013). Changes go through a pull request with CI and SonarCloud passing.

Data survived a Pod deletion

A test row was written, postgres-0 was deleted, a new Pod came back in about 5 seconds with a new IP, and the row was still there.

Bad change caught before apply

A YAML edit landed inside the StatefulSet's storage template. The syntax check passed, but a server-side dry run refused it as an immutable field.

Quality gate finding fixed

SonarCloud flagged containers with no ephemeral-storage requests or limits. They were added, so one container cannot fill the node's disk.

Stuck rollout explained

A rolling update paused because the new Pod could never become Ready without a database. Once PostgreSQL existed, the rollout finished on its own.

For the interview

How to explain it

"FreshTrack is a food expiry tracker I built for my own household. It is three small Python services and PostgreSQL on Kubernetes. Every change goes through a CI pipeline that tests the code, scans the image and ships only what passed, and I verify each piece in the cluster before I call it built."

Why is the database a StatefulSet and the api a Deployment?

The api Pods are interchangeable, like line cooks. The database needs a fixed name and its own disk that comes back after a restart. A StatefulSet gives postgres-0 both, and I proved it by deleting the Pod and reading the data back.

What is the difference between readiness and liveness?

Liveness asks "is the process stuck?" and restarts it. Readiness asks "can it serve right now?" and only stops traffic. My /ready checks the database; /health does not, so a database outage never restarts healthy api Pods.

How do you keep secrets out of the image and out of Git?

The manifests only reference a Secret by name and key with secretKeyRef. The values are created from a file outside the repo. Next, OpenBao and External Secrets Operator will create that Secret for me, and Reloader will restart Pods when it changes.

How do you know the image you run is the one you tested?

CI scans the image, then ships that same saved file. It is tagged with the commit SHA and the cluster pulls it by digest, so the bytes cannot change.

How would you find out something is wrong?

That is the plan for milestone 6: Prometheus for numbers, Loki for logs, Grafana to see both, and Alertmanager to tell me. Today I find problems with kubectl get, describe, logs and events, which is also how I would dig in after an alert.

Why only one component talking to the database?

The rules (valid locations, date types, the 3-day window) live in one place. The web app and the reminder job ask the api, which also keeps the NetworkPolicy simple: only the api may reach port 5432.
